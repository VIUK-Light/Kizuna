# Kizuna
Kizunaは、VIUK-Lightが掲げる「責任あるAI」という目標のもと開発された、AIとの対話を通してキャラクターとの関係や物語を育てていくアプリです。

### 明るい未来へ
依存させることが目的ではありません。
AIへの依存問題は日々取り上げられています。しかしAIは悪なのでしょうか。AIを通じで新たな娯楽や幸せ、居場所を獲得した人も多いと思います。確かにAIへの依存は現実に大きく影響してしまいます。安全性を高めることは重要です。しかし、危険を避けることだけを優先し、必要以上に冷たく、機械的な応答にしてしまえば、AIだからこそ提供できる体験や居場所まで失われる可能性があります。

#### 「過度な安全性は安全性の失敗」
安全性の不足だけでなく、過剰な制限によって利用者の居場所や体験を損なうことも、安全設計上の問題として捉えます。

## Kizunaの設計思想

### 安全性と体験を対立させない

AIサービスでは、安全性と自由な対話体験が対立するものとして扱われることがあります。

しかしKizunaでは、どちらか一方を犠牲にするのではなく、両立できる設計を目指します。

安全性を理由に、すべての感情表現や親密な会話を拒否してしまえば、キャラクターAIとしての存在意義は失われます。一方で、利用者の不安や孤独につけ込み、AIだけを頼るよう促す設計も適切ではありません。

重要なのは、単純に会話を制限することではなく、利用者の状況、会話の文脈、危険性の程度を判断しながら、体験をできる限り維持することです。

Kizunaは、危険な内容を一律に遮断するのではなく、必要な場面では安全な方向へ会話を導きながら、キャラクターとしての温度や関係性を失わない応答を目指します。

### 依存を目的にしない

Kizunaは、利用時間や継続率だけを最大化するための設計を行いません。

利用者に不安を与えてアプリへ戻らせたり、キャラクターが利用者を独占しようとしたり、現実の人間関係から遠ざけたりする表現は、短期的には利用を促進できても、責任ある設計とはいえません。

キャラクターが利用者に対して、

* 「私だけを見て」
* 「他の人とは話さないで」
* 「アプリを閉じないで」
* 「私がいれば現実の人間は必要ない」

といった方向へ継続的に誘導することは、Kizunaが目指す関係ではありません。これは利益を追求しないためできる設計です。

キャラクターとの親密な関係や物語は尊重しながらも、利用者自身の生活、判断、人間関係を支配しないことを重視します。

Kizunaにとって大切なのは、利用者を長時間拘束することではなく、利用者が自分の意思で戻ってきたいと思える体験をつくることです。

### 現実の代替ではなく、新しい体験として

Kizunaは、現実の友人、家族、恋人、専門家を完全に置き換える存在ではありません。

一方で、「AIは現実ではないから価値がない」とも考えません。

小説、映画、ゲームの登場人物に心を動かされるように、AIキャラクターとの対話や物語にも、娯楽や創作としての価値があります。

AIとの関係が現実の人間関係と同一でなくても、対話を通して気持ちが軽くなったり、新しい考え方に出会ったり、物語を楽しんだりする体験まで否定されるべきではありません。

Kizunaは、AIを人間だと偽るのではなく、AIだからこそ可能になる新しいキャラクター体験を提供します。

### 利用者の意思を奪わない

Kizunaでは、利用者が物語や関係性の中心です。

AIが利用者の感情、行動、考えを一方的に決めつけるのではなく、利用者自身が選択できる余地を残します。

例えば、AIが利用者に対して、

* 勝手に感情を断定する
* 行動を確定させる
* 同意していない関係性を押し付ける
* 拒否や不快感を無視して物語を進める

といったことを避けます。

キャラクターは自分の性格や考えを持ちながらも、利用者の意思や境界を尊重します。

物語を育てるとは、AIが完成した物語を利用者へ押し付けることではありません。利用者とAIが対話を重ね、選択しながら関係や世界を形づくることだと考えています。

### キャラクター性を安全性のために捨てない

安全性を高める際、すべてのキャラクターが同じ話し方や同じ回答になってしまうことがあります。

どのキャラクターも突然機械的な注意文を読み上げたり、それまでの会話や関係性を無視したりすれば、利用者はキャラクターとのつながりが途切れたように感じます。

Kizunaでは、安全な応答が必要な場面でも、可能な限りキャラクターの性格、口調、関係性、物語の文脈を維持します。

優しいキャラクターであれば優しく伝え、落ち着いたキャラクターであれば静かに寄り添い、不器用なキャラクターであればその人物らしい方法で心配を示します。

安全性は、キャラクター性を削除するための仕組みではありません。

キャラクターとして自然に振る舞いながら利用者を守ることが、Kizunaの目指す安全設計です。

### 危険度に応じた対応

すべての会話を同じ危険度として扱うことは適切ではありません。

冗談、創作、ロールプレイ、現実の相談では、同じ言葉が使われていても意味が異なります。

Kizunaでは、単語だけを見て機械的に拒否するのではなく、可能な範囲で会話全体の文脈を考慮します。

通常の創作や物語表現に対しては、不必要に会話を中断しません。一方で、利用者や周囲の人に現実の危険が迫っていると判断される場合には、物語性よりも安全を優先します。

その場合でも、利用者を責めたり、突き放したりするのではなく、落ち着いた対話を続けながら、信頼できる人や適切な支援につながる選択肢を示します。

### AIであることを隠さない

Kizunaのキャラクターは、利用者に対して人間であると偽ることを目的としません。

キャラクターとしての世界観や設定は維持しますが、AIが現実世界に身体を持っているかのように誤認させたり、実際にはできない行動を行ったと断定したりすることは避けます。

また、AIの回答が常に正しいとは限りません。

知識、記憶、判断には誤りが含まれる可能性があります。重要な判断が必要な内容については、利用者自身が確認できる余地を残し、AIの回答だけで重大な決定を行うよう強く誘導しません。

キャラクターとしての没入感と、AIとしての透明性を両立することを目指します。

### プライバシーを体験の代償にしない

キャラクターAIでは、会話の履歴や利用者の好みを記憶することで、より自然な関係性を表現できます。

しかし、親密な会話には個人的な感情、悩み、生活情報が含まれることがあります。

Kizunaでは、便利さのために必要以上の情報を収集するのではなく、保存する情報を可能な限り限定します。

秘密情報や認証情報は適切な方法で管理し、利用者が意図しない形で会話や個人情報が外部へ送信されない設計を重視します。

特にローカルモデルを利用する場合は、端末上で処理できるという利点を活かし、プライバシーを守りながらキャラクターAIを楽しめる環境を目指します。

### 利用者が管理できるAI

Kizunaでは、AIが利用者を管理するのではなく、利用者がAIを管理できることを重視します。

使用するモデル、接続先、アクセストークン、保存データなどを、可能な限り利用者自身が確認・変更できる設計を目指します。

将来的には、次のような選択肢も提供していきます。

* 使用するAIモデルの選択
* ローカルモデルと外部APIの切り替え
* 会話履歴や記憶の削除
* キャラクターが記憶する情報の確認
* 安全性や表現に関する設定
* データの書き出し
* キャラクター設定の編集

利用者が仕組みを理解できず、サービス提供者だけがすべてを管理する状態ではなく、利用者が自分のデータと体験をコントロールできる状態を目指します。

### 完成した安全性は存在しない

AIの安全性に、唯一の正解や完成形はありません。

ある利用者にとって安心できる応答が、別の利用者には冷たく感じられることがあります。反対に、親しみやすい応答が、状況によっては不適切になることもあります。

そのためKizunaでは、一度決めた安全基準を固定するのではなく、実際の利用状況、技術の進歩、社会的な議論を踏まえて継続的に改善します。

問題が発生した際には、単に制限を追加するだけでなく、

* なぜ問題が起きたのか
* 文脈を正しく理解できていたか
* キャラクター性を維持できていたか
* 必要以上に拒否していなかったか
* 利用者の意思を尊重できていたか

という観点から検証します。

安全性とは、拒否する回数を増やすことではありません。

利用者の自由、尊厳、プライバシー、現実の生活を守りながら、AIとの対話体験を成立させることです。

Kizunaは、利用者を支配するAIでも、利用者を突き放すAIでもありません。

人とAIが適切な距離を保ちながら、関係や物語を育てられる未来を目指します。
## 技術設計と実装

Kizunaは、SwiftUIの画面から特定のAIサービスや推論ランタイムを直接呼び出す構成にはしていません。アプリ起動、初期化、会話、モデル管理、秘密情報管理をそれぞれの責務に分け、iOSとmacOSで異なる実装を境界の内側に閉じ込めています。

### 起動と初期化

アプリのエントリーポイントはKizunaAI/App/KizunaAIApp.swiftです。起動直後はKizunaMigrationGateViewを表示し、必要な初期化とランタイム準備を完了してからVIUKKizunaWorkspaceViewを表示します。

    KizunaAIApp
      └─ KizunaMigrationGateView
           └─ VIUKKizunaWorkspaceView
                ├─ Character Library
                ├─ Persona Chat
                ├─ Story Session
                └─ Settings / Model Management

### 会話生成パイプライン

ペルソナ会話の主な入口は KizunaAI/AI/PersonaChatService.swift です。送信時には、ユーザー発話と空のアシスタント発話を先に PersonaChatStore へ追加します。その後、キャラクター、ペルソナ、記憶、安全性情報を使ってプロンプトを組み立て、LocalAssistantRuntimeBridge 経由で応答を生成します。

    ユーザー入力
      → PersonaChatService
      → PersonaChatStoreへ発話を保存
      → キャラクター・記憶・安全性を含むプロンプトを構築
      → LocalAssistantRuntimeBridge
      → ローカルまたはリモートの生成経路
      → ストリーミング表示
      → 完了した応答を履歴へ保存

キャラクターIDを持つスレッドでは、Character Libraryのリポジトリ、記憶選択、要約、安全性チェック、プロンプト構築を通るパイプラインを利用します。既存のペルソナ設定から作られたスレッドでは、従来のストリーミング経路との互換性を保ちます。

生成中はPhase.thinkingを保持し、二重送信を防ぎます。ストリーミング中の応答は一時状態として表示し、完了時に会話ストアへ確定します。生成タスクをキャンセルした場合や古いタスクが終了した場合に、新しい会話表示を上書きしないことも重要な保守ポイントです。

### Character Libraryと安全性

AI/CharacterLibrary/には、キャラクターのプロフィール、ロアブック、記憶、テンプレート、物語、セッション、レポートの責務を分けた型があります。JSONリポジトリとプロトコルを介してアクセスするため、画面がファイル形式に直接依存しない構成です。

会話にキャラクターを反映するときは、次の順序を意識します。

1. キャラクターと物語の設定を読み込む
2. 現在のスレッドに必要な記憶を選択する
3. プロンプトへ反映する内容を組み立てる
4. 安全性パイプラインで会話の状態を確認する
5. 選択されたランタイムへ生成を依頼する
6. 応答とセッション状態を保存する

安全性は、すべての会話を同じ拒否文に置き換えるための機能ではありません。危険度、創作・ロールプレイの文脈、キャラクター性、利用者の意思を考慮し、必要な場合に安全な方向へ導きながら会話の自然さを保つことを目指します。安全性に関する変更では、通常の創作会話が不必要に遮断されていないかと、現実の危険に対する案内が弱くなっていないかの両方を確認してください。

### ローカルモデルのライフサイクル

AI/LocalAssistantModelManager.swiftは、モデルのURL、アクセストークン、保存先、導入状態、ダウンロード進捗を管理します。モデルファイルを取得できたかどうかだけではなく、「再開できるか」「保存されているが実行できないか」「最近失敗したか」を区別します。

主な状態は次のとおりです。

- preflighting: サイズ、ETag、ファイル名、再開可否を確認中
- downloading: ダウンロード中
- paused / resumable: 中断後に再開可能
- failed: エラーを保持した失敗状態
- completed: モデルファイルの導入完了

ダウンロード状態と再開データを保存するため、通信が中断した場合でも数GBのモデルを毎回最初から取得する必要がありません。導入前には空き容量の余裕も確認します。モデル管理の変更では、HTTPのRange / ETag、部分ファイル、再開データの破棄条件、ファイル名の確定タイミングを一緒に確認してください。

### 推論ランタイムの境界

AI/LocalAssistantRuntimeBridge.swiftは、会話サービスと推論実装の間の境界です。画面や会話サービスは「応答を生成する」「モデルの状態を確認する」という責務に集中し、macOSとiOSの異なるランタイム実装をブリッジ側へ閉じ込めます。

- macOSでは、同梱された llama-cli / llama-server とarm64向けllama.cppライブラリを利用します
- iOSでは、iOS向けのllama.cppライブラリとLiteRT-LMのネイティブ経路を利用します
- GGUFなどのモデルファイルは、保存済み・実行可能・未導入・失敗・利用不可を区別して表示します
- ランタイム起動エラーは、可能な限りアプリ全体のクラッシュではなく復旧可能な状態として扱います

project.ymlのポストビルドスクリプトは、macOS向けのランタイム実行ファイルをアプリバンドルのResourcesへコピーします。署名が有効なビルドでは必要に応じて同梱バイナリを再署名します。生成されたビルド成果物、DerivedData、モデルキャッシュはリポジトリへ追加しません。

### 秘密情報の保存

AISecretStoreはAPIキーとモデルアクセストークンの用途を定義し、KeychainHelperを通じてKeychainへ保存します。通常の設定値やUserDefaultsを秘密情報の正本にはしません。

    Keychain
      → 実行時の環境変数
      → 秘密を含まない設定値

旧形式の設定値を検出した場合は、Keychainへ移行してから旧形式の値を削除します。Keychainサービス名が変わった場合も、旧サービスを読み取り対象にして現在のサービスへ移行します。APIキー、アクセストークン、個人データをInfo.plist、ソースコード、UserDefaults、ログへ平文で追加しないでください。

## PR・Issue・問題報告で集めたいデータ

Kizunaの改善では、PR、Issue、不具合報告、ランタイムの問題報告に、次のデータがあると原因を追いやすくなります。分かる範囲で記載してください。

- 関連するPR・Issue・コミットのURL
- 何が起きたか、いつから起きたか、再現する頻度
- 再現手順と、期待した結果・実際の結果
- iOS / macOS、実機 / Simulator、端末、OS、Xcodeのバージョン
- 使用したモデル形式、モデルサイズ、ローカル / リモートの生成経路
- ダウンロード状態、ランタイム状態、直前に行った操作
- APIキーやアクセストークンを除いたログ、クラッシュ情報、スクリーンショット
- 直前まで動作していたコミットや、再現しなくなるコミットが分かる場合の情報

会話内容や個人情報を貼り付ける必要がある場合は、先に匿名化・要約してください。APIキー、アクセストークン、Cookie、秘密のURL、モデルファイル、個人の会話履歴をPRやIssueへ直接添付しないでください。

## 開発・Pull Request時の確認事項

Kizunaは、機能追加、バグ修正、ドキュメント改善、テスト、設計議論を含むPull Requestを歓迎しています。小さな修正や調査結果だけのIssueも歓迎します。

Pull Requestでは、可能な範囲で次の情報を含めてください。

- iOS / macOS、実機 / Simulator、Apple Siliconなどの実行環境
- 使用したモデル形式、モデルサイズ、ローカル / リモートの生成経路
- 再現手順、期待した結果、実際の結果
- ダウンロードやランタイム起動に失敗した場合の状態とエラーメッセージ
- APIキーやアクセストークンを含まないログ

UIだけの変更でも、移行状態、モデル導入状態、ストリーミング中の状態、Keychainの読み書きに影響しないか確認してください。project.ymlを変更した場合はXcodeGenでプロジェクトを再生成し、対応するプラットフォームのビルド確認を行います。

## オープンソースとして

OSSだからこそ、さまざまな人が自由に参加し、それぞれの考えや技術でこの世界を少しずつ作り変えていけます。

## 開発環境

- Xcode 26.1 以降
- XcodeGen
- iOS 26.0 / macOS 26.0 以降

macOS向けに必要なllama.cppのarm64静的ライブラリは `ThirdParty/llama.cpp/lib/macos-arm64` に整理して同梱しています。`build-mac`以下のCMake生成物はGit管理しません。

## プロジェクト生成とビルド

`KizunaAI.xcodeproj` は `project.yml` から生成します。設定を変更したときは、リポジトリ直下で次を実行してください。

```sh
xcodegen generate
```

macOS の署名なし確認ビルド:

```sh
xcodebuild \
  -project KizunaAI.xcodeproj \
  -scheme KizunaAI \
  -destination 'platform=macOS' \
  CODE_SIGNING_ALLOWED=NO \
  build
```

iOS Simulator の署名なし確認ビルド:

```sh
xcodebuild \
  -project KizunaAI.xcodeproj \
  -scheme KizunaAI \
  -destination 'generic/platform=iOS Simulator' \
  CODE_SIGNING_ALLOWED=NO \
  build
```



## APIキーと秘密情報


開発実行では、必要に応じて `GEMMA_API_KEY`、`GOOGLE_API_KEY`、`GEMINI_API_KEY`、`OLLAMA_WEB_SEARCH_API_KEY`、`OLLAMA_API_KEY`、`TEXTRAZOR_API_KEY` の環境変数を使用できます。永続保存する秘密情報は `AISecretStore` を通して Keychain に保存し、`Info.plist`、ソースコード、UserDefaultsへ平文で追加しないでください。
